# P4.3-1 SQLite task queue core

This slice adds `fufu_archive.task_queue.TaskQueue`, a callable core for
durable task state. It supports idempotent enqueue, SQLite-safe leasing,
expired-lease recovery, bounded exponential retry/backoff, permanent failure
after the configured attempt limit, success acknowledgement, and inspection.
Each claim also issues a unique lease token. A worker must return both its
worker id and the token to acknowledge or retry; this prevents a stale handle
from the same worker from completing a later lease after expiry and reclaim.

The queue database path is mandatory and must be supplied by the caller. The
module creates and initializes only that path; it never defaults to, opens, or
migrates the Fufu Archive knowledge database. A queue database should be kept
separate from the formal archive database.

This is core functionality only and is not enabled by default. It does not
start workers, scheduling loops, cron jobs, services, HTTP/MCP routes, or
collector task registrations. The companion `fufu_archive.task_runner`
module now offers only a bounded, explicit `run_once(...)` callable; it takes
the queue and handler mapping from the caller and returns after the requested
batch or when the queue is idle. Future integrations should construct a queue
with their own explicit path and invoke this API deliberately. The current
`fufu_archive.collector_tasks` adapter registers only
`collect.hermes.incremental`, and requires every source/checkpoint/archive/
candidate/report path in the task payload; it does not discover production
paths or auto-enqueue work.

The `task_runner` module also exposes a management-only CLI mode:
`--inspect` lists tasks without claiming them, while `--reclaim-expired`
explicitly performs lease recovery and exits. Both require the explicit
`--queue-db` path and neither starts a scheduling loop.

Queue pause state is persisted in the queue database. `--pause` and
`--resume` change that state explicitly; `--control-status` reads it, and a
runner refuses to claim new tasks while paused. Existing running leases are
not silently cancelled by pausing.

`--retry-failed <task_id>` is an explicit operator action that moves one
failed task back to `queued`, clears its stale lease/error, and preserves its
attempt count. It therefore does not silently bypass the configured retry
limit.

The read-only `TaskQueue.summary()` contract returns all four status counts,
the persisted pause state, and lease visibility (`active`, `expired`, missing
expiry, and sorted owners). The runner CLI's `--summary` prints this object;
`--inspect` continues to return task snapshots, including lease owner, token,
and expiry. Neither inspection mode claims, reclaims, or otherwise updates
task rows.

The read-only `TaskQueue.health()` / `TaskQueue.read_only_health(path)`
contract performs SQLite `integrity_check` and required-table inspection without
creating a missing database, enabling WAL, initializing schema, reclaiming
leases, or changing pause state. The CLI exposes this as `--health`; because
the path is checked before constructing a writable `TaskQueue`, a health probe
on a missing or damaged queue remains genuinely non-mutating and reports a
machine-readable failure instead of repairing the database implicitly. The
CLI exits `0` when the check is healthy and `1` for a missing, unreadable, or
structurally incomplete queue, making it suitable for an external health probe.

`run_once()` catches ordinary handler/unknown-task exceptions, stores a bounded
class-and-message error through the queue retry path, and preserves retry
backoff and terminal failure metadata. It deliberately catches no
`BaseException`, so cancellation and process-control exceptions are not
converted into task failures. The collector adapter validates every explicit
path and rejects destination collisions before enqueue; enqueue remains
idempotent and never invokes collection.
