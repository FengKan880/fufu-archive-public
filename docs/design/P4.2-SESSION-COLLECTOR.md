# P4.2 Session Collector

The source of truth for Hermes session candidate collection is
[`src/fufu_archive/session_collector.py`](../../src/fufu_archive/session_collector.py).
It is repository-owned, uses only Python standard-library imports, and is
covered by [`tests/test_session_collector.py`](../../tests/test_session_collector.py).

The existing Hermes profile entry point remains at
`<profile-root>\scripts\fufu_archive\session_candidate_collector.py`.
It is a thin compatibility wrapper that delegates to the repository module
and preserves the existing CLI arguments and behavior. Do not maintain a
second implementation there.

This slice keeps state.db access read-only, emits dry-run review candidates,
keeps child-agent logs separate, and redacts sensitive content. P4.2-2 adds a
versioned, atomically saved collector checkpoint with an `(ended_at,
session_id)` watermark and immutable `profile:session_id:content_sha256`
processed identities. Ended-session collection accepts an explicit
`--profile`/`profile=` value; omitted callers use the conservative `unknown`
profile and do not infer or discover Hermes paths. Saving remains opt-in
through `--commit-state`; the default
invocation does not mutate the checkpoint. Source archive tables, cron, and
automatic candidate commits remain out of scope. Active-session capture is
specified separately in P4.2-5 below.

The ended collector introspects the read-only `messages` schema for optional
columns. In particular, a legacy database without `tool_name` is accepted;
tool names/count metadata are then conservatively unavailable rather than
fabricated. Required session/message fields and coverage limitations remain
explicit in the output manifest.

`source_schema_report(path)` (also exposed as `validate_source_schema` and
`audit_source_schema`) provides a deterministic read-only schema audit. It
reports sorted columns, missing required fields, and the optional
`messages.tool_name` fallback. Collection refuses a source that is missing a
required field with a safe schema error before reading session rows.

Ended rows are ordered numerically by finite `ended_at`, then by session ID;
equal timestamps therefore have stable ordering. Active (`ended_at IS NULL`)
rows are deferred. Invalid or non-finite `started_at`/`ended_at` values are
reported as `invalid_timestamp_fields` skips and cannot advance a checkpoint.
Message fingerprints retain source order, IDs, recognized roles, and safe
content/tool-name metadata, so inserted, removed, unknown, tool, or malformed
rows produce a new content version without emitting excluded bodies.

The checkpoint and source archive readers remain compatible with pre-profile
records. Legacy processed keys and archive records without a profile are
treated as belonging to `unknown` for compatibility. An explicitly named
profile does not treat those legacy records as its own, so two profiles that
reuse a session ID and content digest are both retained. New source records
and candidate payloads persist the profile in their top-level record,
identity, and traceability fields; explicit-profile candidate filenames are
also profile-scoped.

### Profile identity compatibility contract

Ended-session source identity is explicit and uses the stable triple
`(profile, session_id, content_sha256)`. The callable helper is
`processed_identity(session_id, content_sha256, profile="unknown")` and
returns `profile:session_id:content_sha256`; the CLI exposes the same value
through optional `--profile`. Callers that omit the profile use `unknown`.
The collector never infers a profile from a database path or discovers
Hermes profile directories.

Checkpoint reads recognize both new profile-prefixed keys and legacy
`session_id:content_sha256` keys. Legacy keys and source records without a
profile are treated as `unknown`; they are retained when a successful run
saves a new checkpoint/archive. An explicitly named profile does not consume
an unprofiled legacy identity, so profiles sharing a session ID and content
hash produce separate checkpoint entries and source records. Existing
unprofiled candidate payloads remain valid for `unknown`; explicit profiles
use profile-scoped filenames and persist the profile at the payload,
identity, and traceability levels.

The compatibility default does not identify which historical Hermes profile
created an unprofiled record. Complete P4.2 source coverage remains outside
this slice, including validation against all real Hermes schemas, a fully
consistent source snapshot, attachments/truncation/unknown formats, and
message-level recovery.

## P4.2-3: durable local archival

The collector's default invocation remains a dry-run. It reads the explicitly
provided Hermes `state.db`, writes only its explicitly provided report files,
and does not create a source archive, candidate payload, checkpoint update, or
Fufu Archive database write. Archival is an explicit operation:

```text
python -m fufu_archive.session_collector \
  --db <hermes-state.db> \
  --state <collector-checkpoint.json> \
  --output-dir <report-dir> \
  --archive \
  --source-archive <source-archive.json> \
  --candidate-dir <candidate-payload-dir> \
  --commit-state
```

`--source-archive` is also an explicit archival opt-in; `--archive-path` is a
compatibility alias. `--candidate-dir` (also accepted as
`--candidate-output-dir`) is required when review candidates are present. All
paths are caller-selected. The collector rejects a source/archive/state/report
collision and a source/archive/state/candidate destination collision before
writing.

## P4.2-4: explicit incremental-run lifecycle

P4.2-4 adds the one-shot `--incremental-run` operation and the callable
`incremental_run(...)`. It requires explicit paths for the read-only Hermes
database, checkpoint, source archive, candidate payload directory, and report
output. The report output is a stable JSON/Markdown pair: a directory produces
`incremental-run.json` and `incremental-run.md`, while a `.json` or `.md` path
selects that pair by stem. Re-running the same database overwrites the same
report pair; it does not create timestamped report copies.

Example:

```text
python -m fufu_archive.session_collector --incremental-run \
  --db <hermes-state.db> \
  --state-checkpoint <collector-checkpoint.json> \
  --source-archive <source-archive.json> \
  --candidate-dir <candidate-payload-dir> \
  --report-output <report-dir>
```

The lifecycle is:

1. Validate all input/output paths and reject collisions.
2. Open `state.db` with SQLite `mode=ro` and `query_only=ON`; scan ended
   sessions in stable `(ended_at, session_id)` order. The checkpoint watermark
   remains an ordering/progress marker, while the collector rechecks earlier
   rows and uses `(profile, session_id, content_sha256)` identities to skip
   unchanged records and capture appended or changed content. Active sessions are
   counted only for reporting.
3. Build source records, sensitive quarantine manifests, pending candidate
   payloads, the report pair, and the next checkpoint in per-destination
   private staging directories. Each staging directory is created beneath its
   destination parent so `os.replace` remains same-filesystem even when
   caller-selected outputs use different volumes. Validate every staged
   JSON/JSONL archive, payload, report, and checkpoint before publication.
4. Publish the staged archive, candidate files, and report pair as a
   recoverable batch. Existing archive records and valid candidate files are
   preserved; only unseen identities are added. All per-destination staging
   directories are removed after success or rollback.
5. Publish the checkpoint last. If staging or publication fails, the previous
   checkpoint and previously published source/candidate outputs are restored;
   the failed run cannot advance the watermark.

Staging is destination-local: each staged file is created in a temporary
directory under its destination's parent directory before `os.replace`.
This keeps the replacement on the destination filesystem on Windows even
when the archive, candidate directory, reports, and checkpoint are on
different volumes. The temporary directories are removed after successful
publication and on staging or publication errors. This is a filesystem
placement invariant only; it does not claim power-loss durability or
exactly-once publication semantics.

The ended-session outcome remains explicitly `deferred_unsupported` in this
operation. Active rows are not captured by `--incremental-run`, copied,
deleted, or treated as complete.

## P4.2-5: explicit active-session snapshots

Active capture is a separate one-shot operation and callable,
`--active-snapshot` / `active_snapshot_run(...)`; it does not reuse the ended
session watermark path. It requires explicit paths, a profile, and a quiet
window:

```text
python -m fufu_archive.session_collector --active-snapshot \
  --db <hermes-state.db> \
  --state-checkpoint <ended-session-checkpoint.json> \
  --profile <hermes-profile> \
  --snapshot-archive <active-snapshots.json> \
  --report-output <active-report-dir> \
  --quiet-seconds 60 \
  --last-message-at <unix-seconds> \
  --now <test-clock-unix-seconds>
```

The ended checkpoint argument is collision-checked only; it is never read or
written by this mode. The explicit quiet policy is `now - last_message_at >=
quiet_seconds`. A callable can provide `now` and a mapping or callable can
provide per-session `last_message_at` to make tests deterministic. If the
Hermes `messages` table exposes a recognized timestamp column, the newest
valid message timestamp is used. If it does not, capture requires the caller's
explicit `last_message_at`; the ordered stable message IDs remain the
conservative snapshot boundary and reports say
`message_timestamps_unavailable`. Missing or insufficient quiet time is
reported as `deferred_quiet_window`; it publishes no snapshot and never
advances an ended-session checkpoint.

Each active snapshot identity contains `profile`, `source`, `session_id`, and
the ordered list of message IDs and SHA-256 content hashes (including tool
rows for change detection). The snapshot hash is the canonical hash of that
identity. User/assistant bodies may be retained in a source-only snapshot;
tool bodies are never emitted, while tool names/counts and safety scanning are
retained. Sensitive sessions produce a redacted blocked manifest with no
message bodies. Parent/child sessions remain separate, and child sessions are
reported as separate child-agent sessions rather than merged into a parent.

The read uses one explicit SQLite read transaction on a `mode=ro`,
`query_only=ON` connection, so the session and visible messages come from one
consistent source view. Snapshot records are append-only in the explicit
active-snapshot archive. Resumed sessions with no message change replay
idempotently; appended or changed messages produce a new immutable record
keyed by a new snapshot hash and preserve earlier records.

Active snapshots are source-only lifecycle material: they are excluded from
formal KB search, candidate payload generation, candidate approval/commit, and
all Fufu Archive database writes. When the session later ends, the existing
ended-session collector remains responsible for its formal candidate/archive
processing. This operation has no scheduler, cron installation, automatic
active capture, source deletion, or production-session cleanup claim.

### Active snapshot archive format

The active mode writes a separate UTF-8 JSON (or JSONL) archive with format
`fufu-archive.hermes-active-snapshot`, version `1`, and
`archive_type: "active_snapshots"`. Each record has `record_type:
"active_snapshot"` or `"blocked"`, a `snapshot_hash`, and an identity like:

```json
{
  "profile": "example",
  "source": "desktop",
  "session_id": "session-id",
  "message_fingerprints": [
    {"id": 1, "content_sha256": "..."}
  ],
  "snapshot_hash": "..."
}
```

The archive is append-only by snapshot hash. A replay does not rewrite the
archive; an appended message produces another record while retaining the
earlier version. Active records include `formal_kb: {"searchable": false,
"candidate": false}` as an explicit boundary. The archive is not the formal
Fufu Archive database and is not read by KB search.

### Source archive format

The canonical destination is a UTF-8 JSON file with this envelope:

```json
{
  "format": "fufu-archive.hermes-source",
  "version": 1,
  "archive_type": "source",
  "records": [
    {
      "format": "fufu-archive.hermes-source",
      "version": 1,
      "record_type": "session",
      "session_id": "…",
      "content_sha256": "…",
      "identity": {"session_id": "…", "content_sha256": "…"},
      "traceability": {
        "source_db": "…",
        "session_id": "…",
        "source": "…",
        "title": "…",
        "started_at": 0,
        "ended_at": 0,
        "end_reason": "…",
        "parent_session_id": null,
        "message_count": 0
      },
      "messages": [
        {"source_message_id": 1, "role": "user", "content": "…"},
        {"source_message_id": 2, "role": "assistant", "content": "…"}
      ],
      "tool_calls": {"count": 1, "names": ["…"]},
      "content_recovery": "user_assistant_messages_only"
    }
  ]
}
```

Each record is keyed by the stable triple `(profile, session_id,
content_sha256)` both in its explicit `identity` object and at the record top
level. The message list
keeps the original user/assistant text and source message IDs in source order,
which is sufficient to reconstruct the conversational text. Tool message
bodies are never read into an output record; only tool call count and names are
retained. The digest is a canonical hash of ordered, safe message
fingerprints. Each fingerprint contains only the ordinal, valid message ID
(or null), recognized role (or null), a SHA-256 content fingerprint,
content-present flag, and safe tool-name metadata. Changes to excluded tool
bodies, unknown-role rows, null content, and malformed fields therefore
produce a new identity without writing those bodies to an archive.

Every new ended-session record also carries a `coverage_manifest` (and a
backward-compatible short `coverage` view). The canonical manifest has
integer counts for `message_rows`, `user_assistant_bodies`,
`tool_bodies_excluded`, normal assistant `tool_call_only_turns`,
`unknown_roles`, `malformed_or_missing_content`, `invalid_message_ids`, and
`invalid_fields`, plus sorted
`unknown_role_names` and `message_count_mismatch`. `status` is `complete` only
when every observed row is a valid user/assistant body; excluded tool bodies
and assistant tool-call-only turns are separately counted declared exclusions,
while unknown roles, missing/empty content without positive tool-call evidence,
non-string/structured content, invalid ID/field, or
declared/observed count mismatch makes it `partial`. Sensitive quarantine
changes the status to `blocked` and writes no message bodies. The manifest's
`cleanup_qualification_blocked` is true for partial and blocked coverage;
incomplete coverage can never qualify a future source cleanup operation.

Unknown roles are counted and named but their bodies are never emitted.
Malformed or missing content is counted conservatively; an invalid message
ID is omitted from the retained message list but represented by a safe
fingerprint. An invalid essential session field makes that session
`malformed_session_fields` and prevents checkpoint advancement for that row;
it does not abort collection of other ended sessions. Legacy records without
a manifest remain readable and are normalized on load as `legacy: true` and
partial coverage, rather than being rejected or treated as lossless.

Destinations ending in `.jsonl` use the same versioned record envelope one
record per line. Both forms are atomically replaced after validation. Existing
records are retained unchanged at the record-value level; a replay adds only
previously unseen identities. A malformed existing archive is an error and is
never overwritten. Temporary files are created beside their destination,
flushed and fsynced, then published with an atomic replace. For the
multi-output incremental and active-snapshot runs, this destination-local
staging rule applies independently to every archive, candidate, report, and
checkpoint output.

For compatibility, a legacy source record without `profile` is read as
`unknown` and is preserved unchanged. New records include `profile` at the
record, identity, and traceability levels. Candidate payloads follow the same
profile-scoped identity, and explicit-profile candidate filenames are isolated
from legacy/default payload filenames.

### Sensitive quarantine

If a selected session matches a sensitive-content rule, the source archive
receives a `record_type: "blocked"` manifest with the same identity and
traceability fields, for example:

```json
{
  "record_type": "blocked",
  "session_id": "…",
  "content_sha256": "…",
  "blocked": {
    "reason": "sensitive_content",
    "sensitive_kinds": ["api_key"],
    "raw_content_written": false,
    "message_bodies": "excluded"
  }
}
```

No user, assistant, or tool body is written for a blocked session. Tool bodies
are scanned for the same safety decision but remain excluded regardless of the
result. A blocked manifest is not a candidate and cannot become formal
knowledge by replay.

### Candidate payload lifecycle

Each safe review candidate gets one atomically written JSON file in the
explicit candidate directory. Its `format` is
`fufu-archive.hermes-candidate`, its `version` is `1`, and its
`review_status` is `pending`. It contains the same stable identity,
traceability, ordered user/assistant messages, tool metadata, and collector
candidate metadata as the source record. It also records
`formal_archive.kb_add_called: false` and `formal_archive.committed: false` as
an explicit boundary: this operation never imports `kb_add`, calls the MCP
adapter, approves a candidate, commits a document, or modifies the formal
Fufu Archive database.

Candidate filenames include a sanitized session ID and the full content hash,
so a replay resolves to the same path. A valid existing file with the same
identity is preserved; a corrupt file or an identity collision fails without
overwriting it. If a run is interrupted between independent atomic file
publishes, retrying repairs the missing file and does not duplicate the source
record or candidate payload. Checkpoint advancement remains separately
opt-in through `--commit-state` and occurs only after archival and report
preparation succeed.

`load_candidate_payload(path)` validates both legacy unprofiled payloads and
new profile-scoped payloads. Missing profile fields are interpreted as
`unknown` in memory and missing coverage manifests are classified as legacy
partial coverage; malformed manifests or inconsistent profile/identity fields
are rejected before any archive output is published. Incremental reports
include aggregate coverage counters and `status_counts` for complete, partial,
and blocked records.

This slice archives only the ended sessions already selected by the existing
read-only collector. It does not capture active sessions, install cron,
automatically commit candidates, delete source data, or clean up any source or
production session files. Human review remains the gate before any future
formal archive operation.
