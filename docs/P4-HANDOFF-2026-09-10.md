## P4.2 cross-volume publication slice

The incremental and active-snapshot multi-output publishers now create each
staged file in a temporary directory under that file's destination parent.
This preserves same-filesystem `os.replace` behavior when caller-selected
outputs are on different Windows volumes. Staging directories are cleaned up
on success and on staging/publication failure; existing recoverable batch
rollback remains in place. This does not claim power-loss durability or
exactly-once semantics.

Focused acceptance evidence for this slice:

- `tests/test_session_collector.py`: JSONL archive coverage, destination-local
  staging placement, and staging cleanup assertions.
- Parent acceptance commands are recorded in
  `tmp/codex-p42-cross-volume-handoff.md`.

## P4.2 profile identity slice addendum

The ended-session collector now accepts an explicit optional `profile`, with
the conservative default `unknown`. Its durable identity is
`profile:session_id:content_sha256`; callers use
`processed_identity(session_id, content_sha256, profile="unknown")`, and the
CLI uses `--profile`. No profile path inference or Hermes directory discovery
is performed.

Checkpoint readers continue to recognize legacy
`session_id:content_sha256` keys. Legacy checkpoint/archive/candidate records
without a profile remain readable as `unknown` and are not rewritten unless a
successful run is already publishing a new checkpoint/archive. Explicit
profiles do not consume those legacy identities. Source records and pending
candidate payloads persist profile in their top-level, identity, and
traceability fields; explicit-profile candidate filenames are isolated while
the `unknown` filename remains backward-compatible.

This is a narrow identity/compatibility slice, not a complete P4.2
acceptance. Real Hermes schema variation, consistent source snapshots,
attachments/truncation/unknown formats, locks, and message-level recovery
remain open limitations. Coverage-manifest handling is now implemented for
ended-session source records, candidate/report output, unknown roles,
malformed content, excluded tool bodies, sensitive blocked records, and
legacy records without a manifest.

## P4.2 coverage-manifest addendum

The ended-session collector now emits a deterministic `coverage_manifest` for
each candidate, skipped/blocked item, child log, source record, and candidate
payload, plus an aggregate report manifest. It counts retained
`user_assistant_bodies`, excluded `tool_bodies_excluded`, normal assistant
`tool_call_only_turns`, `unknown_roles`, `malformed_or_missing_content`,
`invalid_message_ids`, and `invalid_fields`.
The status is `complete` only when every observed row is a valid retained
user/assistant body; excluded tool rows, unknown roles, malformed/missing
content, invalid IDs/fields, or a declared/observed message-count mismatch
make it `partial`. Sensitive quarantine makes it `blocked`. Tool and unknown
message bodies are never emitted; safe ordered fingerprints are used for
change detection, so changes to excluded or unmodeled rows are not silently
treated as unchanged.

`cleanup_qualification_blocked` is true for partial and blocked coverage.
Incomplete coverage must block any future source cleanup qualification;
user/assistant-only text is not a lossless session backup. Legacy source
records without a manifest remain loadable and are classified as
`legacy: true` partial coverage. No source cleanup, production collection,
or formal knowledge write is authorized by this slice.
